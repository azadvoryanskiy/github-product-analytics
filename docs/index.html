Data quality · GitHub public events

A third of the activity vanished overnight. Did users leave?

No. Nothing happened to users. The pipeline started throttling — and a third of what was still arriving had never been human in the first place.

The answer in three lines

  1. The 34% fall on 24 May 2025 was a rate cap on the data feed, not a change in behaviour. It hit every event type and every kind of account by the same third, and no hour of any day since has gone above ~169,000 events.
  2. The cap is not a random sample. It keeps 58% of the busiest hour and 75% of the quietest, so the data under-represents exactly the most active users.
  3. Of the events that do arrive, 37.5% are automation — and the filter everyone uses, "login ends in [bot]", finds only 25.3 of those 37.5 points.

FIRST

The standard checklist passes, and proves nothing

Duplicates, missing values, broken types — run on 108 million rows from June 2025, it returns 47 duplicated rows and nothing missing. That is 0.00004%.

If cleaning stopped there, the conclusion would be "the data is clean". The checklist tests whether the data is well-formed. It says nothing about whether it is true.

01

Users do not leave in unison

Before 24 May the line has a shape: weekdays at 5.5–5.8M, weekends lower. That is a human rhythm. Then it falls 34% between a Friday and a Saturday and runs flat for three months. Users do not leave overnight and in unison.

02

It is a lid, not a decline

Every event type fell by the same third — pushes −34.7%, pull requests −31.1%, stars −35.4%, issues −35.7%. So did every kind of account. A real change in how people work does not move code review and stars by the same number.

The hour-of-day view shows why: the shape of the day flattens against a lid. Peak-to-trough was 1.49× before and 1.17× after. Anyone measuring when peak load happens would now get a 22% different answer, with nothing about users having changed.

03

The standard bot filter finds two thirds

Three rules, each catching what the previous one misses: accounts GitHub itself marks as bots; accounts active 20+ hours a day; accounts doing hundreds of events of one type into one or two repositories. The volume floor sits far above people — the median account produces 2 events a day.

The standard filter finds two thirds of the problem. The rest are ordinary user accounts running scripts, which GitHub has no reason to mark. One of them, freefastconnect, pushed to a single repository 1.8 million times across 114 days.

04

Checking the rule against GitHub itself

The API cannot confirm these are bots — it reports "type": "User", which is correct. So the check had to come from elsewhere: does GitHub eventually remove them? I sampled 150 accounts per rule and asked.

Flagged accounts are 8 to 12 times more likely to be gone (Fisher exact, p = 1.4 × 10⁻⁵ and 3.9 × 10⁻⁹). That is corroboration, not proof — but it rules out the rules firing at random.

What I would change

  • Check the pipe before explaining the number. A 34% drop should trigger one query — events per hour — before anyone writes a sentence about user behaviour. Cheap enough to run as an alert on any metric moving more than 15% in a day.
  • Report automation next to the metric, not instead of it. On a developer platform the automation is part of the product. The mistake is letting it sit inside "active users" unlabelled.
  • Do not trust [bot] alone, and re-run the behavioural rules quarterly — the biggest undeclared account here did not exist two years ago.
  • Key on the immutable id. Over 138 days, 2,289 logins were used by more than one account and 119,857 accounts changed their login.

How I would know it worked: take the ten metrics on the main dashboard, compute the automation share and the completeness check across two years of history, and count how many past decisions would have gone differently. That is the number to put in front of the team.

How it was built

  • GH Archive, 138 consecutive days, 560,839,725 events
  • Python streams the feed hour by hour into Parquet
  • DuckDB for the analysis, all of it on a laptop
  • GitHub REST API for the validation sample

Caveats. Public activity only — private repositories are invisible. The rules are thresholds, and thresholds are judgement; the sensitivity is worth checking before the numbers are used for anything. The deletion check is correlation, not proof. The 2026 feed is worse than anything described here, which is why the analysis stops in September 2025.
